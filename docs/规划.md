# OTA规划

## 规划 

**这个规划，9月份正式启动，前期需要做agent测试（等阿里云企业认证之后进行，在阿里云上部署服务器）。**

**自研应用级OTA**：定时轮询版本清单 → 下载 → 校验 SHA256 + Ed25519 签名 → 解压到新目录 → 原子切换符号链接 → 健康检查，失败自动回滚
- 直接复用 config.toml 已预留的 ota_poll_interval / ota_config_url / config_version；代码、模型资产、配置分包独立版本，低频更新

**严肃考虑OTA和后端结合的做法，实现一体的机器人认证+后端保存重要秘钥+context组合，这样文档都不用ota了。这里的考虑结合LeanBrain的边缘脑规划。这个思路要先考察下云内访问的速度。** 

## 需求

有三项ota需要
1. 程序本身的更新
2. data中机器人信息文件等的更新

### OTA云端功能
1. 为用户服务端部分
    - 前端，让用户可以上传新的数据文件
    - 进行用户资料整理的后端，具备agent功能，能够根据用户的文件，周期性或者手动触发资料整理。
    - 文档整理的结果必须符合机器人的实时性要求，例如整理后的文档数量要控制在15k之内，尽可能小

2. 一个机器人管理的部分
    - 后端，机器人区分 型号、软件版本、机器人唯一标识、机器人更新key
    - 为机器人安排不同的更新时间，避免一窝蜂同时更新。
    - 机器人用正确的标识和key，能够从云端下载最新的数据文件。
    - 机器人可查询是否有新的程序文件，并获取更新程序文件的时间（）。
    - 机器人用正确的标识和key，能够从云端下载新的程序文件，替换当前的程序文件。

### OTA本地功能
1. 机器人按约定的时间夜间主动拉取数据文件，并更新自己的数据。
2. 机器人按约定的时间拉取程序文件，并更新自己的程序。
